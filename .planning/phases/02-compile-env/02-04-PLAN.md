# Phase 02 Plan 04: Enhanced Diagnostic Parsing and Build Reporting

## Objective

Enhance the compile environment with comprehensive diagnostic parsing for all major compiler formats, multi-line diagnostic context capture, linker diagnostic separation, and build artifact reporting with human-readable sizes.

## Context

- `src/embedagent/tools/_base.py` — contains `run_subprocess_streaming` from 02-03 and basic diagnostic parsing
- `src/embedagent/tools/compile_ops.py` — contains `list_compilers`, `configure_build_env`, `run_build` from 02-02/02-03
- `src/embedagent/tools/runtime.py` — tool registration and catalog

## Tasks

### Task 1: Enhance diagnostic parsing for all compiler formats in _base.py

**Type:** auto

Enhance `parse_diagnostics` in `ToolContext` to handle:

1. **GCC diagnostic format** — add regex pattern for GCC-style diagnostics
2. **Multi-line diagnostic context** — capture code snippet lines and caret lines that follow diagnostic entries
3. **Linker diagnostic separation** — detect and classify linker errors separately from compiler errors
4. **Preserve backward compatibility** — existing single-line Clang/MSVC parsing must continue to work

**Implementation details:**

- Add `GCC_DIAGNOSTIC_RE` pattern matching GCC's `file:line:column: level: message` format
- Add `LINKER_DIAGNOSTIC_RE` patterns for common linker error signatures (`ld:`, `LINK :`, `collect2:`)
- Modify `parse_diagnostics` to accept an optional `capture_context` parameter (default `True`)
- When `capture_context` is enabled, look ahead up to 3 lines after a diagnostic match for:
  - Lines that appear to be code snippets (contain `|` or are indented)
  - Caret lines (`^` pointing to error location)
- Store captured context in a `context` field on each diagnostic entry
- Add `diagnostic_category` field with values `"compiler"`, `"linker"`, or `"other"`
- Keep `MAX_DIAGNOSTICS = 200` limit
- Ensure `normalize_level` handles GCC's `"fatal error"` the same as Clang

**Verification:**
- Existing tests in `test_tools_package.py::TestToolRuntimeExecute::test_run_build_parses_diagnostics` must pass
- New tests for GCC, MSVC, multi-line context, and linker diagnostics

### Task 2: Add artifact size and linking diagnostic reporting to compile_ops.py

**Type:** auto

Enhance `run_build` in `compile_ops.py` to report build artifacts and linker diagnostics.

**Implementation details:**

- After build completes, scan the build directory (and subdirectories) for artifact files:
  - Extensions: `.exe`, `.dll`, `.lib`, `.a`, `.so`, `.o`, `.obj`, `.elf`, `.bin`, `.out`, `.wasm`
- Report each artifact with:
  - `path`: relative path from workspace
  - `size_bytes`: raw size
  - `size_human`: human-readable string (B, KB, MB with 1 decimal place for KB/MB)
- Add `_format_size` helper for human-readable sizes:
  - < 1024: `"%d B" % size`
  - < 1024*1024: `"%.1f KB" % (size / 1024.0)`
  - >= 1024*1024: `"%.1f MB" % (size / 1024.0 / 1024.0)`
- Add `_scan_build_artifacts` helper in `compile_ops.py`
- In `run_build` observation data, add:
  - `artifacts`: list of artifact info dicts (max 50)
  - `artifact_count`: total count
  - `linker_diagnostics`: subset of diagnostics where `diagnostic_category == "linker"`
  - `linker_error_count`: count of linker errors
- Only scan for artifacts if build exits successfully (exit_code == 0 and not timed_out)
- Only report artifacts within the workspace boundary (use `ctx.resolve_path` or relative paths)

**Verification:**
- New test: build produces artifacts, verify sizes reported
- New test: failed build reports no artifacts but has linker diagnostics
